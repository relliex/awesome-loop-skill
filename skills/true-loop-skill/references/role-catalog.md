# 软件 / 系统工程域案例附录：28 岗位 → 核心角色的映射

本文件是 [role-design.md](role-design.md) §1（软件/系统工程）案例的附录，
**只在项目属于软件/系统领域且规模较大**（多模块 / 多服务 / 受监管行业）
时读取。其他领域请用 role-design.md 的对应案例，并按 SKILL.md §2 生成法
现场生成本项目的团队——不要照搬本文件的岗位。

## 设计原则

原版 28 个独立岗位在实践中会导致派工爆炸，执行模型为省事直接
角色扮演全部岗位——这是 v1 失效的直接原因。本目录把 28 岗位
收敛为"少量实例工厂 + 按需变体"：岗位差异体现在**任务包的目标
函数、信息边界与禁区**上，而不是体现在"必须派一个新岗位"上。
这里的岗位只作为软件域生成团队时的参考素材。

## 专项变体派出规格

每个变体 = 在对应核心角色模板上追加以下内容：

**QA-安全面**
- 目标：在授权范围内验证权限、隔离、输入处理与敏感数据。
- 额外输入：威胁模型（来自 ARCH-安全变体）。
- 禁止：超出授权范围的扫描与攻击；把代理判断当作法律意见。
- 报告：复现步骤 + 影响评估。

**QA-性能面**
- 目标：证明性能目标不达标，或给出实测达标证据。
- 禁止：无实测数据的优化建议；估算冒充实测。
- 报告：方法、环境、负载数据、原始结果。

**QA-运行面（SRE）**
- 目标：验证日志、健康检查、降级与恢复路径。
- 禁止：未真实演练却声称恢复能力已证明。
- 报告：演练步骤与真实执行记录。

**QA-集成面（契约/迁移强化）**
- 目标：跨模块调用、事务、幂等、迁移与历史兼容。
- 禁止：用纯 Mock 结果声称真实集成通过。
- 报告：契约偏差清单 + 迁移前后数据证据。

**ARCH-安全变体**
- 目标：威胁模型、信任边界、最小权限转化为可测试的安全验收条款。
- 产出并入 prd.md（或 design.md，若启用）与 acceptance.md。
- 禁止：把代理判断当作法律意见、正式认证或持证审计。

**ARCH-数据变体**
- 目标：数据模型、迁移、回滚与保留策略。
- 禁止：把不可逆迁移描述成简单回滚；默认生产数据可删。

**ARCH-算法 / ML 变体**
- 目标：评估方案、数据划分、防泄漏与可复现性规则。
- 验收必须包含"独立评估实例用冻结数据重跑指标"。

**PM-UX / PM-UI 变体**
- 目标：把交互、状态（含空态/失败/取消/恢复）与无障碍要求转化为
  可判定验收条款，写入 acceptance.md。
- 禁止：仅凭截图宣称无障碍合规。

## 新增岗位的规则

行业特殊需要（支付、医疗、嵌入式等）新增岗位时，派发前必须定义：
岗位 ID 与启用条件、目标函数、输入、禁区、上游与下游、必要人工
资质或审批。禁止派出职责未定义的"万能专家"自由发挥；代理不能
替代法定持证人员、人工审计或真实授权。
