- 日期：2026-09-17
- 输入：用户原话（见 §1，逐字转录）
- 交付目标：skill 升级完成并同步到仓库
- 上游依据：无（本文件为根需求）

## 1 用户原话转录（锚点原文，不得改写）

> 目前这个项目只是针对工程化，程序开发之类的，但是如果是更多的场景，这个
> skill 效果就不太好看了，所以，接下来要对这个 skill 进行一次大更新，不是
> 穷举出所有岗位，而是要让模型学会自己产出真实岗位与提示词，当使用这个
> skills，我希望的流程是，模型会分析用户需求的完整性，如果用户的需求太
> 抽象，模型会通过多轮用户选择器来与用户交互，完整的了解用户的真实需求，
> 最终产生方案后会再来一次用户选择器询问用户"是否接受当前方案"以及
> "接下来会为你编排 xxx 团队，是否同意"，当用户全部同意之后，模型会基于
> 产生的 prd 去基于 skills 中的教学案例去构建一个完整的任务团队，里面会
> 包含大量专家，其中不乏对抗性的就像是开发和测试一样，当团队构建完成之后
> 会再构建出一个 team.md，然后总结 team 中有哪些成员然后通过用户选择器
> 与用户交互，当用户完全同意且满意之后，由主模型调控，子代理完成任务的
> loop 系统就开始运行

## 2 背景与问题

v2 是面向软件交付设计的：正文以固定的 8 个角色（PM/ARCH/DEV/REV/QA/FIX/
AUD/DOC）和软件词汇（构建、自测、缺陷、盲测）为主干。换到写作、研究调查、
设计、运营方案、数据分析、翻译、课程设计等场景时，固定岗位不成立，"构建
与自测"没有对应物，skill 的效果明显下降。

根因：v2 把"岗位"当成了知识（写死在文档里），而不是把"如何生成岗位"当成
能力（教给模型）。

## 3 需求条目（R）

- **R1 域无关**：SKILL.md 正文不得再以固定岗位表为主干；所有岗位由模型在
  运行时为本项目生成。软件域角色只能作为教学案例出现。
- **R2 岗位生成教学**：skill 必须教会模型"自己产出真实岗位与提示词"——
  提供可复用的生成方法，并配跨领域教学案例（≥6 个领域，含软件域），
  每个案例给出该域生成后的角色清单、对抗配对，以及至少一段完整提示词。
- **R3 需求完整性分析**：使用 skill 的第一阶段必须对用户需求做完整性分析，
  按固定维度清单识别缺口（抽象、缺失、矛盾、不可判定）。
- **R4 多轮选择器澄清**：需求过于抽象时，必须通过多轮"用户选择器"
  （结构化提问工具）与用户交互，直至无阻断缺口。每问给选项与推荐项；
  用户答复逐字落盘。
- **R5 方案确认门**：产出方案（prd.md + acceptance.md）后，必须用选择器
  询问"是否接受当前方案"，且明示这是阻断门。
- **R6 团队编排门**：方案通过后，模型基于 prd 与教学案例生成完整任务团队
  （含对抗性专家），产出 team.md（成员、目标函数、信息边界、对抗配对、
  预算、派发顺序），并用选择器展示成员摘要、询问"接下来为你编排 xxx
  团队，是否同意"。
- **R7 满意判定与迭代**：G3 需要用户"完全同意且满意"；含糊答复视为未通过，
  调整后重新请求确认。
- **R8 循环运行**：全部门通过后，进入"主模型调度、子代理执行"的 loop。
- **R9 不回退**：保留 v2 已确立的核心机制——真实派发、盲测轮次与连续通过
  计数、`.loop/` 磁盘状态、锚定协议与 anchors 逐字摘录、预算不重置、诚实
  交付状态。词汇域无关化，机制不减。
- **R10 仓库同步**：SKILL.md、references、双语 README、仓库 Description
  与新流程保持一致。

## 4 非目标

- 不提供、不穷举任何领域的固定岗位库；
- 不改 skill 名（`true-loop-skill`）、不改仓库结构基线；
- 不引入除"选择器提问"之外的强制用户交互（内部步骤仍自动推进）。

## 6 验收标准（AC，可执行、可判定）

- **AC1** SKILL.md 正文中不存在固定岗位名单式主干；软件域角色仅作为案例
  引用（人工核对 + grep 抽查）。
- **AC2** `references/role-design.md` 存在，含 ≥6 个领域案例，每案例含
  角色清单 + 对抗配对 + 完整提示词示例。
- **AC3** SKILL.md 定义 G1/G2/G3 三道门：触发时机、必含信息、失败路径。
- **AC4** `references/state-format.md` 给出 team.md 完整字段定义与门记录字段。
- **AC5** SKILL.md 给出需求完整性分析维度清单（≥6 维度，可勾选）。
- **AC6** SKILL.md ≤ 500 行；frontmatter 的 name/description 合规且描述覆盖
  新流程（澄清 → 方案确认 → 团队确认 → 循环）。
- **AC7** 锚定协议与 anchors 逐字摘录、连续 CLEAN 计数、预算不重置三条
  机制在 v3 中可检索到且语义未削弱。
- **AC8** 双语 README 描述新流程；仓库 Description 与之一致。
- **AC9** 对抗自检：把新 SKILL.md 与本需求文档交给一个独立子代理，要求
  "证明它不满足 R1–R10 或 AC1–AC8"；对有效发现修复或明确记录不接受的理由。

## 7 约束与风险

- 预算：本次升级的派发预算 ≤ 8 次真实子代理调用；
- 风险 1：域无关化会稀释 v2 的强约束 → 用"三种原型 + 生成后自检清单"维持
  强制力（对应 R9）；
- 风险 2：团队生成可能膨胀出大量无独立产物的角色 → 必须写入"每个角色有
  独立产物与判据，禁止为热闹造角色"的硬约束（对应 R6）；
- 风险 3：选择器多轮提问可能让用户疲劳 → G1 默认 ≤3 轮、每轮 ≤4 问。
