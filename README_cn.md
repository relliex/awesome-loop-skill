# awesome-loop-skill

**True Loop** — 域无关的对抗式交付闭环，供 AI 代理使用。

主模型只做调度。需求先与你澄清，再为你的项目现场生成一支专家团队；
真正的工作——写作、编码、调研、设计、分析——由相互隔离的子代理执行，
它们看不到你的对话，也看不到彼此的辩解。

## 为什么

主流的"agent loop"是串行的：一个模型在自己的上下文里深度循环，看到
一切、评定一切。项目一旦大到超出模型能力，失败方式是可以预测的：

- **自己给自己打分。** "我想完成"和"验收标准"待在同一个上下文里。阻力
  最小的路径就是压低标准、美化数据、用自评替代真实验证。结果看起来
  完成了，指标也达标了——但交付物在实际使用中根本不过关。
- **循环稀释自己的指令。** 长循环必然触发上下文压缩。最初的目标只剩
  一份有损摘要；到第 N 轮，模型优化的已经不是你的需求，而是需求的转述。

## 原理：上下文隔离不是缺陷，是特性

许多 agent / harness 提供的子代理**看不到主对话**。子代理的全部世界，
就是派出时收到的那份任务包。

这通常被当作限制。本 skill 把它当作全部设计的出发点：

- **主模型只是调度器，别的什么都不做。** 它维护状态、写任务包、机械
  核验证据、路由问题。禁止它产出交付物——不写代码、不写文案、不写方案、
  不写测试。
- **每个子代理只有一个任务。** 只看得到自己任务包的实例，既不会被项目
  其他部分分心，也无法替别的角色找借口。
- **对抗是结构性的。** 生产者的唯一目标是让自己的工件通过冻结判据；
  对抗验证者的唯一目标是**证明它不达标**——它必须真实地检验工件，找到
  真实问题才是干得好。两者永远看不到对方的报告。

## 动态团队，而不是固定岗位表

本 skill 不以岗位库为主干，带的是**岗位生成法**（SKILL.md §2）与八个
领域的**教学案例**（[references/role-design.md](references/role-design.md)），
另附一份永非必读的软件域附录。每个项目现场长出自己团队，所有岗位都是
三种原型的域内实例化：

| 原型 | 目标函数 | 信息边界 |
|------|----------|----------|
| 生产者 | 产出指定工件，使其通过冻结判据 | 判据、素材、自己的写范围 |
| 对抗验证者 | 用实际执行证明指定工件不达标 | 工件、判据、真实验证手段；绝不看生产者自评 |
| 仲裁与审计者 | 定义并冻结判据；校验追踪链 | 全部工件与证据 |

生成之后还有自检门：每个交付物都有生产者；每个关键交付物都有信息隔离
且**真能失败它**的对抗者；判据由第三方定义；不存在"万能专家"角色。

内置领域案例：软件/系统工程、长文写作、研究调查与尽调、设计/UX、运营
与活动方案、数据/ML、翻译与本地化、课程设计——每例都给出生成后的角色
清单、对抗配对与完整提示词模板。

## 流程

```
G1  澄清   主模型分析需求完整性
           → 多轮用户选择器提问，直到无阻断缺口
G2  方案   方案角色产出 prd.md + 验收标准
           → 通过选择器问"是否接受当前方案？"
G3  团队   基于方案与教学案例生成角色 → team.md
           → 向你展示团队名单
           → 通过选择器问"接下来为你编排这支团队，是否同意？"
运行       主模型调度、隔离子代理执行：生产、盲测对抗验证、返工
           → 判据真实通过后独立审计 → 交付
```

有两件事刻意不做成可选项：**产出方案之前先问你**，**组建团队之前先问你**。
含糊的答复（"随便""你看着办"）不算同意。

## 让规则真正成立的机制

1. **真实派发，否则不做。** 每个阶段必须产生真实的子代理调用与落盘产物；
   没有证据的 "PASS" 无效。宿主没有子代理工具时，skill 以
   `BLOCKED_CAPABILITY` 停止而不是角色扮演——这一点实测过：没有派发工具
   的模型拒绝假扮角色，干净地挂起并落盘。（串行自检降级模式只在用户
   明确同意时启用，且必须标注"未经独立子代理验证"与"自评风险"、给出
   你可自行复跑的人工复核步骤；高风险项目禁用。）
2. **盲测对抗轮次。** 验证按轮进行，每轮全新实例。通过需要连续 ≥2 轮
   全部攻击面无问题（高风险 3 轮）；任何阻断问题都会清零计数；"未发现
   问题"必须附实际尝试清单——空报告视为未执行。
3. **磁盘状态（`.loop/`）。** state.json、方案、验收标准、team.md、任务包、
   报告、问题、证据全部落盘。上下文压缩丢不掉循环。
4. **锚定抗稀释。** 每份任务包必须包含 `anchors` 段：从其所服务的冻结
   文件中**逐字摘录**原文。逐字摘录没法凭记忆完成，而且可以机械校验
   （grep）——所以主模型被迫在给子代理下命令前真的去读方案，子代理执行
   的也是冻结原文，而不是主模型转述的二手版本。
5. **原话决策记录。** 每次选择器的用户答复都逐字落盘，事后你可以逐条核对
   交付与当初拍板是否一致。

## 安装

需要具备真实子代理派发能力的宿主（Agent/Task 工具且返回真实结果，最好
支持单消息并行派发）、文件读写与命令执行，以及用于用户门禁的结构化提问
工具。

```bash
# 用户级（全局可用）
git clone https://github.com/relliex/awesome-loop-skill ~/.agents/skills/true-loop-skill

# 或项目级
git clone https://github.com/relliex/awesome-loop-skill .agents/skills/true-loop-skill
```

> 安装目录必须命名为 `true-loop-skill`，即 skill 的 `name`。

## 快速开始

然后直接提问，例如：

> 用 true-loop-skill 写一篇 6000 字的技术解读，讲清楚 RAG 对后端工程师
> 意味着什么。预算：40 次派发。

或

> 用 true-loop-skill 做一个极简 CLI 待办工具（add / list / done，
> JSON 持久化）。预算：40 次派发。

你会在任何交付工作开始之前先被提问（G1）、被请求确认方案（G2）、被请求
确认团队（G3）。这正是 skill 在按设计工作。

## 设计历史

- **v1** 是一份 1158 行的治理文档，定义了 28 个固定岗位。模型对它全部
  认同——然后在同一个上下文里把所有角色自己串行演了一遍。
- **v2** 用结构取代政策：隔离子代理、盲测对抗轮次、磁盘状态、PRD 锚定。
  每条规则要么是一次真实的子代理调用，要么是一个磁盘文件，要么是一段
  无法凭记忆产出的逐字摘录。但 v2 仍是软件形状的，固定 8 个角色。
- **v3**（当前）走向域无关：模型为每个项目**生成**团队（依据生成法 +
  跨域教学案例），并用三道用户门（澄清 → 方案 → 团队）让你在任何工作
  开始前掌握决定权。

塑造 v2 并延续至今的教训：**口号敌不过结构。** 一条不落实为"单次派发的
形状"或"磁盘产物的存在"的规则，只是建议。
