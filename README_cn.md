# awesome-loop-skill

**True Loop** — 对抗式子代理工程闭环，供 AI 编程代理使用。

主模型只做调度。PRD、设计、开发、审阅、破坏性测试与审计，全部由
相互隔离的子代理执行——它们看不到你的对话，也看不到彼此的辩解。

## 为什么

主流的"agent loop"是串行的：一个模型在 own 上下文里深度循环，
看到一切、评定一切。项目一旦大到超出模型能力，失败方式是可以预测的：

- **自己给自己打分。** "我想完成"和"验收标准"待在同一个上下文里。
  阻力最小的路径就是压低标准、美化数据、用自评替代真实验证。
  结果看起来完成了，指标也达标了——但项目在实际使用中根本不过关。
- **循环稀释自己的指令。** 长循环必然触发上下文压缩。最初的目标只剩
  一份有损摘要；到第 N 轮，模型优化的已经不是你的需求，而是需求的
  转述。

## 原理：上下文隔离不是缺陷，是特性

许多 agent / harness（ZCode、Claude Code、Codex CLI 等）提供的子代理
**看不到主对话**。子代理的全部世界，就是派出时收到的那份任务包。

这通常被当作限制。本 skill 把它当作全部设计的出发点：

- **主模型只是调度器，别的什么都不做。** 它维护状态、写任务包、机械
  核验证据、路由缺陷。禁止它写产品代码、测试和 PRD；没有落盘产物
  就宣布"完成"也是禁止的。
- **每个子代理只有一个任务。** 只看得到自己任务包的实例，既不会被
  项目其他部分分心，也无法替别的角色找借口。
- **对抗是结构性的。** DEV 实例的唯一目标是让构建与自测真实通过；
  QA 实例的唯一目标是证明项目**不**满足验收标准——它必须真实运行
  项目，找到真实缺陷才是干得好。两者看不到对方的报告。开发想方设法
  完成，测试想方设法找茬——这股张力替代了"请务必严格检查"。

### 角色

每个角色是一个实例工厂；按任务包随时派出全新实例。

| 角色 | 目标函数（实例心中只有这个） | 信息边界 |
|------|------------------------------|----------|
| PM   | 把用户目标变成可判定的验收标准 | 用户目标、访谈记录、现状调查 |
| ARCH | 把验收标准变成可实现、可测试的设计 | PRD、现状调查 |
| DEV  | 在写权限内实现，让构建与自测真实通过 | PRD、设计、自己的写权限范围 |
| REV  | 找出 diff 中的偏差与风险 | PRD、设计、完整 diff——没有开发的辩解 |
| QA   | 通过实际运行证明项目不达标 | 验收标准 + runbook；永远看不到开发报告与既往轮次 |
| FIX  | 消除指派缺陷且不引入新问题 | 含复现步骤的缺陷包 |
| AUD  | 证明交付追踪链完整，或指出断裂 | 全部产物 + 证据 |
| DOC  | 让交接文档与真实行为一致 | 最终实现 |

## 让规则真正成立的机制

1. **真实派发，否则不做。** 每个阶段必须产生真实的子代理调用与落盘
   产物；没有证据的 "PASS" 无效。宿主没有子代理工具时，skill 以
   `BLOCKED_CAPABILITY` 停止而不是角色扮演——这一点实测过：没有派发
   工具的模型拒绝假扮 PM，干净地挂起并落盘 `blocked_on`。
2. **盲测轮次。** 测试按轮进行，每轮全部使用全新 QA 实例。通过需要
   连续 ≥ 2 轮全攻击面 CLEAN（高风险项目 3 轮）；任何阻断缺陷都会把
   计数清零；CLEAN 必须附"实际尝试过的攻击清单"——空报告视为未执行。
3. **磁盘状态（`.loop/`）。** state.json、冻结的 PRD/验收、任务包、
   报告、缺陷、证据全部落盘。上下文压缩丢不掉循环。
4. **PRD 锚定（抗稀释）。** 每份任务包必须包含 `anchors` 段：从其所
   服务的冻结需求文件中**逐字摘录**原文。逐字摘录没法凭记忆完成，而且
   可以机械校验（grep）——所以主模型被迫在给子代理下命令前真的去读
   PRD，子代理执行的也是冻结原文，而不是主模型转述的二手版本。
5. **先访谈，后冻结。** P1 的流程是：分析 → 询问用户 → 原话落盘 →
   冻结 PRD，每条需求必须可溯源到任务输入或某条用户决策；溯源不到的
   需求不得写入。

## 一图看懂一次运行

```
P0 启动       能力门禁 + 探针派发 + 搭建 .loop/
P1 需求       PM 分析 → 访谈用户 → 冻结 PRD 与验收标准
P2 设计       ARCH：模块划分、并行写权限切分、接口契约
P3 实现       DEV × k 并行（写权限互不重叠）+ runbook
P4 审阅       REV 审完整 diff → 缺陷
P5 盲测       QA × m 并行（全新实例、互不重叠的攻击面）
P6 返工       FIX → REV 复验 → 重建候选 → 回 P5，计数清零
P7 审计       AUD 校验 需求 → 实现 → 证据 链 → 最终报告
```

## 安装

需要具备真实子代理派发能力的宿主（Agent/Task 工具且返回真实结果，
最好支持单消息并行派发），以及文件读写与命令执行。

```bash
# 用户级（全局可用）
git clone https://github.com/relliex/awesome-loop-skill ~/.agents/skills/true-loop-skill

# 或项目级
git clone https://github.com/relliex/awesome-loop-skill .agents/skills/true-loop-skill
```

> 安装目录必须命名为 `true-loop-skill`，即 skill 的 `name`。

## 快速开始

然后直接提问，例如：

> 用 true-loop-skill 做一个极简 CLI 待办工具（add / list / done，
> JSON 持久化）。预算：40 次派发。

主模型会先访谈你（P1）再冻结 PRD，然后进入循环。写代码之前先被提问
——这正是 skill 在起作用。

## 设计历史：v1 为什么失败

v1 是一份 1158 行的治理文档，定义了 28 个岗位和大量"禁止"。实践中
模型对它全部认同——然后在同一个上下文里把所有角色自己串行演了一遍。

塑造 v2 的教训：**口号敌不过结构。** 一条不落实为"单次派发的形状"
或"磁盘产物的存在"的规则，只是建议。v2 里的每条规则，要么是一次
真实的子代理调用，要么是一个磁盘文件，要么是一段无法凭记忆产出的
逐字摘录。
